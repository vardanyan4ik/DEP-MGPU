## 1. Цель и постановка задачи

Цель работы — объединить справочник клиник, сведения о приёмах и прейскурант, проверить качество данных, очистить записи с сохранением журнала и карантина, построить реляционную модель и рассчитать выручку. Корректность расчёта проверяется независимо средствами SQLite и pandas.

Исходные данные **синтетические**: они создаются генератором из [студенческого ноутбука](ЛБ2_Консолидация_вариант_8.ipynb) при `VARIANT = 8` и фиксированном `seed = 1056`. Результаты иллюстрируют методику и не описывают реальные клиники.

## 2. Аудит качества

Для каждой колонки построен профиль с типом, заполненностью, количеством уникальных значений и примерами. Результаты сохранены в [source_profiles.csv](pw2_work/source_profiles.csv); полный журнал проблем — в [quality_issues.csv](pw2_work/quality_issues.csv).

| Измерение | Обнаруженная проблема | Затронуто строк |
|---|---|---:|
| Полнота | пустой регион клиники; пропуски объёма; пропуски цены | 1; 13; 17 |
| Уникальность | повтор клиники; повторы `event_id`; повторы `price_id` | 1; 26; 40 |
| Согласованность | даты в формате `дд.мм.гггг`; цены строками с пробелами и ₽ | 13; 17 |
| Валидность | отрицательные цены | 20 |
| Ссылочная целостность | приёмы с неизвестной клиникой; цены без исходного события | 20; 0 |
| Точность | цены за границами правила `3 × IQR` | 0 |

Числа в строках таблицы относятся к **отдельным проверкам**: одна исходная запись может иметь несколько проблем, поэтому их нельзя складывать как число уникальных дефектных записей. Для цен границы `3 × IQR` составили от −40 229,35 до 70 353,01 ₽. Статистический выброс был бы сигналом для сверки с прейскурантом, а не автоматическим доказательством ошибки.

Связи `клиника → приём` и `приём → ценовая строка` имеют кардинальность **1:N**. В исходных данных на один приём приходится в среднем **2,01** ценовой строки, максимум **4** с учётом дубликатов. Профиль связей приведён в [cardinality.csv](pw2_work/cardinality.csv). Такая структура приводит к размножению объёма при прямом `JOIN`.

## 4. Реляционная модель и расчёт выручки

В [SQLite-базе](pw2_work/consolidation_variant_8.sqlite) созданы таблицы `entities`, `events` и `prices`. Поля `entity_id`, `event_id` и `price_id` объявлены первичными ключами. Внешние ключи связывают приём с клиникой и цену с приёмом; ограничения `CHECK` требуют положительных `volume_units` и `unit_price`. Созданы индексы по внешним ключам и дате приёма. Проверка `PRAGMA foreign_key_check` нарушений не выявила.

Для приёма e с ценами pₑᵢ и числом ценовых строк nₑ сначала рассчитывается средняя цена:

$$
\bar p_e = \frac{1}{n_e}\sum_{i=1}^{n_e} p_{e,i}.
$$

Выручка клиники s с приёмами E(s):

$$
R_s = \sum_{e\in E(s)} v_e\,\bar p_e,
$$

где vₑ — число пациентов в приёме. Простое среднее — допущение учебной модели. Если известны объёмы по видам услуг, требуется взвешенная цена.

Корректный SQL сначала сворачивает цены до уровня приёма, затем соединяет результат с объёмом:

```sql
WITH price_per_event AS (
    SELECT event_id, AVG(unit_price) AS avg_price
    FROM prices
    GROUP BY event_id
)
SELECT e.entity_id,
       SUM(ev.volume_units * pe.avg_price) AS revenue
FROM entities e
JOIN events ev ON ev.entity_id = e.entity_id
JOIN price_per_event pe ON pe.event_id = ev.event_id
GROUP BY e.entity_id;
```

Прямой `JOIN entities → events → prices` с `SUM(volume_units * unit_price)` повторяет объём приёма для каждой ценовой строки. Поэтому `R_naive = Σₑ nₑ · vₑ · p̄ₑ`, и коэффициент завышения равен `K = R_naive / R_correct`.

| Показатель | Значение |
|---|---:|
| **Корректная выручка** | **14 176 208 192,25 ₽** |
| Выручка наивного `JOIN` | 28 178 724 672,35 ₽ |
| **Коэффициент завышения K** | **1,9877** |
| Максимальное расхождение SQL и pandas по клинике | 0,005 ₽ |

Независимый расчёт pandas группирует цены по `event_id`, объединяет средние цены с приёмами и суммирует выручку по клинике. Разница **0,005 ₽** связана с округлением SQL до копеек. Итоги по клиникам, месяцам и видам услуг сходятся в пределах округления. [Витрина по приёмам](pw2_work/event_mart.csv) и [выручка по клиникам](pw2_work/revenue_by_clinic.csv) сохранены отдельно.

## 6. Управленческие рекомендации

**1. Проверить возможность роста в Новосибирске.** Клиника имеет наименьшее число пациентов в выборке. Следует проверить спрос и свободные часы врачей, затем провести пилот расширения записи. При условии роста числа пациентов на **5 %** и сохранения выручки на пациента сценарная прибавка составит около **32,59 млн ₽ в год**. Это расчётный сценарий, а не прогноз спроса. Эффект проверяется по числу записей, пациентов, времени ожидания и выручке на пациента за четыре недели в сравнении с сопоставимым периодом.

**2. Учитывать сезонность при планировании ресурсов.** Июльская выручка примерно в **1,54 раза** выше мартовской. Персонал и материалы следует планировать по помесячному профилю. Ожидаемый эффект — меньше отказов в записи в пиковые недели и меньше простаивающих смен в слабые месяцы. Для проверки следует измерять отказы, занятость персонала и выручку на рабочий день; этих показателей в исходном наборе нет.

**3. Закрепить корректный расчёт и входной контроль.** Выручку следует считать после свёртки цен до уровня приёма; перед загрузкой проверять ключи, ссылки и диапазоны значений. Это устраняет завышение *отчётной* цифры почти в **1,99 раза** относительно наивного `JOIN`; дополнительной фактической выручки такая правка не создаёт. Проверка — регулярная сверка SQL и pandas, `PRAGMA foreign_key_check` и доли строк в карантине.

## 7. Дополнительное исследование C

Критические автопроверки встроены непосредственно **перед пересозданием и загрузкой SQLite**. Они проверяют полноту и уникальность ключей, даты, числовые типы, положительность объёма и цены, а также внешние ключи. Проверка `3 × IQR` выдаёт предупреждение и не блокирует загрузку без подтверждённой ошибки.

| Пакет | Результат | Причина |
|---|---|---|
| Очищенный | принят | критичные правила соблюдены |
| Отрицательная цена | остановлен до `INSERT` | некорректная цена |
| Неизвестная клиника | остановлен до `INSERT` | нарушена ссылка |
| Повтор `price_id` | остановлен до `INSERT` | повтор первичного ключа |
| Пропуск объёма | остановлен до `INSERT` | неполный приём |

После четырёх отрицательных проверок количество строк в SQLite не изменилось. Результаты эксперимента сохранены в [dq_test_results.csv](pw2_work/dq_test_results.csv).

## 8. Ограничения и итог

В учебных источниках нет числа продаж по каждому виду услуги, затрат, длительности приёмов, численности врачей и истории отказов. Поэтому структура по видам услуг является модельной, а управленческие эффекты требуют проверки на реальных данных.
